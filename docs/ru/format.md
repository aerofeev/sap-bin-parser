# Формат выгрузки

Выяснено на настоящих выгрузках; это действительно запутанная часть.

## Выгрузка описывает сама себя

Выгрузка приходит как zip-архив из zip-архивов по шардам:

```
BSIS.QUERY.zip
  BSIS.QUERY/DATA.0.zip   -> DATA.0.TXT    файл схемы
  BSIS.QUERY/DATA.1.zip   -> DATA.1.BIN    шард с записями
  BSIS.QUERY/DATA.2.zip   -> DATA.2.BIN
```

Файл схемы `DATA.0.TXT` задаёт имя, тип, длину и размер в байтах каждого поля:

```
NAME     TABLE  TYPE  LENG  DEC  SIZE  ROLL     KEY
BUKRS           C     4     0    8     BUKRS
HKONT           C     10    0    20    HKONT
DMBTR           P     7     2    7     DMBTR
```

## Пять типов полей, две кодировки

`C` (символьный), `N` (цифровой текст), `D` (дата, `YYYYMMDD`) и `T` (время, `HHMMSS`)
хранятся в UTF-16BE, по два байта на символ, поэтому `SIZE` всегда равен `LENG * 2`. `P` —
упакованное десятичное число, у которого `SIZE` — это число байтов.

## Упакованное десятичное (COMP-3)

Каждый байт хранит две цифры, кроме последнего: в нём одна цифра и полубайт знака. `0xB` и
`0xD` — отрицательное число, `0xA`, `0xC` и `0xE` — положительное, `0xF` — без знака. `DEC`
задаёт число знаков после запятой; сами цифры запятой не содержат. Поле из одних нулевых
байтов — это null в SAP, а не допустимое значение COMP-3; оно читается как ноль.

## Записи выравниваются по чётной границе

Именно на этом люди теряют полдня. Поля BSIS в примере выше в сумме занимают **125** байт,
но записи идут с шагом **126**: SAP дополняет записи нечётной длины одним байтом, чтобы
каждая начиналась с чётного адреса и её поля UTF-16 оставались выровненными. Ошибётесь — и
каждая запись после первой окажется сдвинута: результат всё равно получится, будет выглядеть
как таблица, а суммы будут неверными.

Отсюда правило `record_size = payload + (payload % 2)`, которое применяют обе реализации.
Если выгрузка всё равно не сходится, `sap-bin probe` оценивает варианты размера по тому,
сколько записей читается без ошибок и делятся ли данные на записи без остатка.

## Неверный размер записи — ошибка, а не предупреждение

Сдвиг почти всегда даёт недопустимые полубайты знака и нерасшифровываемый UTF-16, и парсер
в обоих случаях останавливается с ошибкой, а не пишет правдоподобный мусор. `--on-error skip`
оставляет ошибочные значения пустыми, подсчитывает их и продолжает.

## Одна и та же таблица приходит в двух форматах

В одних выгрузках шарды — это двоичные `DATA.N.BIN` фиксированной ширины, в других —
текстовые `DATA.N.TXT` с разделителем-табуляцией и строкой заголовка (windows-1251, минус в
конце у кредитовых сумм), при одинаковом файле схемы и без каких-либо признаков снаружи
архива. Каждая команда сама выбирает нужный способ чтения. `DATA.0.TXT` — всегда файл
схемы, а `DATA.1.TXT` и дальше — данные.

## Значения

- У текста убираются только NUL и пробельные символы ASCII по краям. Неразрывный пробел —
  это данные, и он сохраняется.
- Даты превращаются в `YYYY-MM-DD`. Пустые даты и даты из одних нулей становятся пустыми.
  Всё остальное проходит без изменений, чтобы необычное значение было видно, а не терялось.
- Время превращается в `HH:MM:SS`. `000000` — это полночь, а не пустое значение.

## На чём проверено

Описание формата получено на настоящих выгрузках SAP ECC: таблицах проводок `BSIS` и
`BSIM`, а также на пользовательской таблице из 61 столбца с полями времени `T` и четырьмя
разными масштабами упакованных чисел в одной записи. Шард `BSIS` из 250 000 записей был
полностью расшифрован в строгом режиме, и итоговый Parquet дал ту же точную сумму `Decimal`,
что и прямой разбор байтов.

В репозитории нет никаких данных. Все тестовые наборы синтетические, их строят собственные
кодировщики библиотек. Чтобы проверить свою настоящую выгрузку:

```bash
python scripts/compare.py YOUR.QUERY.zip --parquet
```

Скрипт конвертирует выгрузку обеими реализациями во временной папке, сравнивает результат
побайтно, сообщает время и всё удаляет. Он никогда не выводит значения полей, поэтому его
вывод можно без опаски вставить в issue.
