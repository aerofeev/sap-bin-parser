# Скорость

Замерено командой `sap-bin bench` на 4-ядерном Intel Xeon 2,1 ГГц, на 126-байтовой записи
BSIS:

| | записей в секунду |
|---|---:|
| Отдельный `.BIN` в CSV, 1 поток | 2,8 млн |
| Отдельный `.BIN` в CSV, 4 потока | 7,8 млн |
| Отдельный `.BIN` в Parquet (zstd), 4 потока | 3,5 млн |
| Zip-архив выгрузки в CSV, 4 потока | 3,6 млн |

Десять миллионов записей (1,26 ГБ):

| | время | пик памяти |
|---|---:|---:|
| через stdin в CSV | 1,3 с | 118 МБ |
| через stdin в Parquet | 2,9 с | 166 МБ |
| загрузка в веб-сервис, Parquet в ответ | 2,8 с | 118 МБ |
| через страницу в Chromium, 1 млн записей в CSV | 2,4 с | |

Потребление памяти не растёт с размером входных данных. Шарды расшифровываются параллельно
пулом рабочих потоков, и у каждого есть свой небольшой канал ограниченного размера к
писателю, который сохраняет порядок вывода. Поэтому быстрый поток ждёт, а не накапливает
результат.

Библиотека на Python конвертирует те же данные примерно в 15–25 раз медленнее, с
идентичным результатом.

Запустите `sap-bin bench`, чтобы замерить свой компьютер.

## В браузере

Там, где может, страница конвертирует в браузере движком, скомпилированным в WebAssembly, в
одном потоке. В Chromium 1,6 млн записей конвертируются со скоростью около 635 000 записей
в секунду в CSV и 780 000 в Parquet, байт в байт как нативный движок. Ни отправки, ни
загрузки нет, так что сеть не играет роли.

## Через интернет

Конвертацию по сети ограничивает сеть, а не движок. CSV, приходящий обратно, обычно вчетверо
больше отправленного zip. Поэтому сервис сжимает текстовые загрузки (zstd, а для браузеров
без него — gzip), и браузер распаковывает их при сохранении. На синтетическом образце zstd
уменьшает CSV в 4,5 раза без заметной цены: 1 млн записей за 0,35 с вместо 0,34 с.
Настоящие выгрузки с повторяющимися балансовыми единицами и дополненными полями обычно
сжимаются сильнее. На медленном канале Parquet ещё меньше. А чтобы сеть не участвовала
вовсе, запустите [приложение](cli.md).
